# LifeInbox 里程碑方法

[English](06-milestone-method.en.md)

## 1. 目的

本文档定义如何通过 LifeInbox 进行学习，同时避免让生成的代码或庞大的路线图取代工程判断。

进度的单位不是一周、一个章节或一个框架，而是一项能够证明其正确性的产品能力。

## 2. 固定的里程碑循环

每个里程碑都遵循同一个循环：

```text
定义需求
-> 定义不变量
-> 实现最小 happy path
-> 注入一个真实的失败
-> 观察错误行为
-> 阅读有针对性的文档
-> 改进设计
-> 添加自动化测试
-> 不看代码解释结果
```

不要一开始就让 Codex 完成全部实现。

## 3. 五行功能卡

实现之前创建这张卡片：

```markdown
## 功能卡

目标：

数据流：

必须始终成立的规则：

可能的失败点：

如何证明正确性：
```

这张卡片应当能在一个屏幕内完整显示。如果做不到，这个里程碑可能过大。

## 4. 编码前的设计问题

对于每个里程碑，只回答与当前切片相关的问题：

- 哪个用户可见的结果发生了变化？
- 哪些数据是权威数据？
- 哪些数据是草稿、派生数据、缓存或外部数据？
- 哪些操作必须具有原子性？
- 哪些事情可能发生多次？
- 哪些事件可能乱序到达？
- 哪些错误可以重试？
- 哪些状态转换是合法的？
- 谁可以读取或修改这个资源？
- 哪些证据能够证明该行为？

当前里程碑不需要 queue、cache、Agent 状态或微服务时，不要提前设计它们。

## 5. 完成定义

只有满足以下条件，里程碑才算完成：

- 用户可见的路径能够工作。
- 已写下产品不变量和数据不变量。
- 至少复现了一个真实的失败。
- 自动化测试证明了重要行为。
- 用户或运维人员能够看到错误状态。
- 相关日志有用，且不会泄露敏感数据。
- 作出有意义的选择时，记录一份简短的架构决策。
- 开发者无需查看代码，就能解释数据流和权衡。
- 明确记录延期工作。

仅仅通过 happy path 不代表完成。

## 6. 必需的证据包

每个里程碑都应留下：

1. 可运行的代码。
2. 自动化测试。
3. 一个有文档记录的失败实验。
4. 更新后的功能卡。
5. 如果作出了真实选择，提供一份简短的 ADR。
6. 更新后的数据流或状态说明。
7. 一段 60 至 120 秒的技术解释。
8. 一条简洁的作品集或面试陈述。

建议的技术解释结构：

```text
用户需求是……
系统必须保证……
我最初的方法是……
它在以下情况下失败……
我通过以下方式修改了设计……
我使用以下方法完成验证……
主要权衡是……
```

## 7. 失败实验模板

```markdown
## 失败实验

预期不变量：

注入的失败：

修复前观察到的行为：

根本原因：

设计变更：

修复后的自动化证明：

剩余限制：
```

实验应针对真实的正确性边界，而不是随意制造一个异常。

## 8. ADR 模板

```markdown
# ADR NNNN：决策标题

## 状态

Proposed | Accepted | Superseded

## 背景

存在哪些产品需求和约束？

## 选项

考虑了哪些现实可行的选项？

## 决策

选择了什么？为什么？

## 后果

哪些事情变得更容易、更困难，或被推迟？

## 验证

哪项测试、指标或实验能够证明这个决策有效？
```

ADR 用于记录决策，而不是编写某项技术的教程。

## 9. 审查流程

在每个里程碑边界，按照以下顺序进行审查：

### 产品审查

- 用户可见的行为是否符合里程碑要求？
- 是否有额外功能进入范围？
- 不确定状态和错误状态是否容易理解？

### 数据审查

- 哪些表和约束发生了变化？
- 权威状态是否与模型草稿及外部状态明确区分？
- 时间语义和删除语义是否明确？

### 失败审查

- 出现重复、超时、崩溃、过期更新和无效输入时会发生什么？
- 哪些失败通过真实 PostgreSQL 或真实 worker 行为进行了测试？

### 安全审查

- 用户或 Agent 工具是否可能超出自身范围？
- 日志或错误中是否暴露私人内容？
- 外部副作用是否经过确认并具备幂等性？

### 学习审查

- 开发者能否解释目的、失败、修复、测试和权衡？
- 开发者能否在没有逐步指导的情况下完成一个相邻改动？

## 10. Codex 协作边界

Codex 可以：

- 解释概念或错误。
- 比较设计选项。
- 提出不变量和边界用例。
- 在设计确定后，为重复性的设置工作搭建脚手架。
- 生成或审查测试。
- 审查 migrations 和 SQL。
- 设计失败注入实验。

开发者应当负责：

- 数据模型。
- Drizzle schema 和 migration 审查。
- 事务边界。
- 时间语义。
- Authentication 与 authorization 策略。
- 重试与幂等策略。
- Agent 工具权限。
- 评测用例和发布阈值。
- 最终验收决策。

## 11. 紧接着要做的里程碑：V1.0

暂时不要开始 AI 提取。

### 功能卡草案

```text
目标：
使用 Drizzle 启动连接 PostgreSQL 的 NestJS API，确保 migrations 可复现，并提供一个真实的
integration test。

数据流：
环境配置 -> pg Pool -> Drizzle client -> PostgreSQL -> 测试断言。

必须始终成立的规则：
Drizzle 是唯一的 ORM；空数据库可以通过已提交的 migrations 达到当前 schema；测试绝不以
开发数据库为目标。

可能的失败点：
URL 无效、数据库不可用、migration 缺失、测试 schema 过期、pool 未关闭、意外安装 TypeORM。

如何证明正确性：
初始化一个空的测试数据库，应用 migrations，执行真实的 Drizzle 连接查询（例如 SELECT 1），
并确认不存在 TypeORM package 或 import。第一个产品表在 V1.1 中引入。
```

### 实现 V1.0 前需要作出的决策

- Node 和 pnpm 的准确版本。
- 依据官方文档验证过的 Drizzle 和 PostgreSQL driver 版本。
- Schema 和 migration 目录。
- 开发数据库和测试数据库的命名。
- 测试隔离方法。
- 开发环境和生产环境的 migration 命令。
- PostgreSQL 不可用时的 health/readiness 行为。

只有 V1.0 通过后，V1.1 才能引入第一个 `InboxItem` 表。

## 12. 第一个产品里程碑：V1.1

### 功能卡草案

```text
目标：
粘贴并保存一条生活通知，然后在 Inbox 中查看它。

数据流：
Next.js 表单 -> POST /inbox-items -> NestJS validation -> service -> Drizzle ->
PostgreSQL -> response -> Inbox 列表。

必须始终成立的规则：
原始文本非空、不超过硬性大小限制、保持内容不变，并且拥有一个稳定标识符和创建时间。

可能的失败点：
payload 无效、数据库不可用、资源不存在、重复内容警告的语义、列表排序不稳定。

如何证明正确性：
使用真实 PostgreSQL 的 API integration tests，并通过一个最小浏览器流程创建并重新加载通知。
```

V1.1 不应包含 LLM 调用、Redis、文件、authentication、vector search 或日历导出。

## 13. 进度台账

使用以下紧凑的状态格式：

```markdown
| 里程碑                | 状态        | 已复现失败 | 自动化证明 | 已完成解释 |
| --------------------- | ----------- | ---------- | ---------- | ---------- |
| V1.0 Drizzle baseline | Not started | No         | No         | No         |
| V1.1 Manual inbox     | Not started | No         | No         | No         |
| V1.1b Manual draft    | Not started | No         | No         | No         |
```

允许的状态：

- `Not started`
- `Design review`
- `Happy path`
- `Failure reproduced`
- `Fix under test`
- `Complete`

这样可以防止一项只完成了部分功能的特性仅仅因为代码已经存在，就被标记为完成。
