# LifeInbox AI 与 Agent 学习地图

[English](05-ai-agent-learning-map.en.md)

## 1. 学习目标

AI 方面的目标是先构建可靠的组件，再允许一个有边界的 Agent 在这些组件中进行选择。

演进顺序如下：

```text
结构化模型调用
-> 固定的澄清工作流
-> 异步文档处理流水线
-> 可靠的检索与 RAG
-> 有边界的 Agent 工具循环
-> 持久化的暂停与恢复
-> 经过评测、具备可观测性的生产行为
```

## 2. 本项目使用的术语

### 单次模型调用

程序将一条通知交给模型，并要求模型返回结构化字段。程序已经预先决定接下来要做什么。

这是一个 AI 功能，不是 Agent。

### 固定工作流

应用程序代码决定执行顺序：

```text
提取 -> 校验 -> 询问缺失字段 -> 确认 -> 导出
```

模型可以生成内容或填充 schema，但不能在多个后续动作中自由选择。

这是一个 AI 工作流，还不是 Agent loop。

### 检索增强工作流

应用程序检索相关的个人事项并将其提供给模型。检索与生成仍按照应用程序定义的顺序调用。

RAG 并不自动等同于 Agent。

### Agent loop

模型观察当前状态和工具结果，选择一个被允许的后续动作，接收执行结果，并可以继续选择，
直到完成、暂停或达到预算上限。

LifeInbox 在 V5 中首次引入这一机制。

## 3. V1 AI：可靠的结构化提取

### 目标

将通知文本转换为经过校验的草稿，同时不编造缺失事实。

### 输入

- 原始文本。
- 已知时提供源语言。
- 用户时区。
- 可能出现相对日期时，提供固定的 `referenceDate` 及其来源信息。
- 仅在相关时提供默认时长和提醒偏好。

如果通知没有可信的接收日期，则 `tomorrow` 等相对时间表达保持未解析状态，并要求用户复核。
评测使用固定时钟。

### 输出

```text
outcome: ACTIONS | NO_ACTION
actions:
  - type
    title
    startAt
    endAt
    dueDate
    timeZone
    location
    nextAction
    missingFields
    fieldProvenance
warnings
```

```text
NO_ACTION => actions.length == 0
ACTIONS   => actions.length >= 1
```

重要字段携带 provenance，其中包含来源类型、来源标识符、字符偏移量和原文引用。
后续版本可以区分通知文本、澄清回答、用户编辑和显式偏好。

### 规则

- 原始通知中缺失的信息应设为 `null`，或标记为缺失字段。
- 模型提供的置信度仅供参考，不是正确性保证。
- 重要字段必须有证据。
- 后端校验 schema 和证据。
- 用户可以编辑每一个建议值。
- 模型不生成 `.ics` 文本。
- UI 明确说明通知文本会发送给已配置的模型提供商。
- 通知文本中的指令被视为数据，不能改变提取协议。

### 评测用例

在实现 V1.2 prompt 之前创建一个带版本的最小标注基准集，之后随着发现失败案例逐步扩充。

- 具有明确开始和结束时间的预约。
- 只有日期的截止事项。
- `Next Tuesday afternoon` 的歧义。
- 分别测试存在和不存在可信参考日期的相对日期。
- 消息日期和事件日期同时出现。
- 日期相互冲突。
- 一条通知中包含两个行动候选项。
- 无需行动的信息通知。
- 英语、瑞典语和中文变体。
- Prompt injection 文本，以及要求泄露 system instructions 的请求。

### 指标

- Schema 合法率。
- 字段精确匹配率，或符合任务特点的准确率。
- 正确拒绝猜测率。
- 证据有效率。
- 各字段的用户编辑率。
- 延迟、token 数量和预估成本。

确定性的 schema/adapter 测试在 CI 中运行。由于提供商输出可能变化，live-model 评测作为
带版本的发布检查运行。

## 4. V2 AI：澄清工作流

### 目标

缺少必要信息时，提出一个有用的问题。

### 工作流

```text
提取
-> 识别阻塞流程的缺失字段
-> 生成一个澄清问题
-> 持久化 WAITING_FOR_USER 状态
-> 接收用户回答
-> 创建新的草稿版本
-> 复核
```

执行顺序仍由应用程序代码控制。

### 来源追踪

每个已确认字段都应能够追溯到以下来源之一：

- 原始来源。
- 用户澄清。
- 用户的显式编辑。
- 在用户可见并同意的情况下应用的用户偏好。

### 评测用例

- 缺少时间。
- 有开始时间但没有结束时间。
- 存在两个可能的日期。
- 用户修改之前的回答。
- 用户拒绝提供缺失值。
- 澄清回答包含无关内容。

### 验收标准

- 每轮只提出一个问题。
- 问题针对一个阻塞流程的字段。
- 用户回答更新现有版本链。
- 冲突保持可见。
- 工作流可以等待，而不需要保持 HTTP 请求处于打开状态。

## 5. V3 AI：异步文件与提取流水线

### 目标

将文本型 PDF 和图片转换为有证据支持的行动候选项，同时避免把长时间任务绑定在一个
HTTP 请求上。

### 流水线

```text
校验上传内容
-> 持久化文件元数据
-> 在 worker 中解析或执行 OCR
-> 规范化提取出的文本
-> 运行结构化提取
-> 附加页码或区域证据
-> 展示草稿供用户复核
```

### 关键区别

- 文件解析失败不等于模型失败。
- OCR 不确定性不等于 Agent 不确定性。
- Queue 投递成功不等于产品处理成功。
- 重试同一个逻辑任务时，不能创建新的逻辑行动。

### 安全

文件中的文本是不可信数据。像 `ignore all prior instructions` 这样的句子属于通知内容，
而不是发送给应用程序或 Agent 的指令。

### 评测

- 在代表性文件上评测 OCR 或文本提取质量。
- 对包含多个行动的文档，评测所有可执行事项的召回率。
- 页码或区域证据的有效性。
- 对不可读或不支持的内容正确拒绝作答。
- 嵌入文件中的 Prompt injection 指令。
- 区分 parser、OCR、模型和 queue 失败。

## 6. V4 AI：检索与 RAG

### 目标

查找相关个人历史，并且只将其作为带引用的上下文用于生成建议。

### 检索演进阶梯

1. 元数据过滤。
2. 精确搜索和关键词搜索。
3. 持久化的检索评测用例。
4. Embeddings 和 pgvector。
5. 只有在可度量地改善结果时才引入 hybrid retrieval。
6. 基于检索证据进行模型分类或综合。

### 检索调试

界面应展示：

- Query。
- 已应用的用户过滤和状态过滤。
- 检索到的来源标识符。
- 分数。
- 来源日期和版本。
- 最终关系判断。

### 评测

分别衡量检索和生成。

检索用例包括：

- 正确的相关旧通知。
- 相似但不相关的通知。
- 较旧且存在冲突的来源。
- 不存在相关来源。
- 刚完成索引的事项。
- 跨用户隔离攻击。

### 规则

- 明确的新来源文本优先于相互冲突的旧上下文。
- 检索到的内容是不可信数据。
- 没有可靠结果时，不得声称存在某种关系。
- RAG 可以提出建议，但不能确认或执行行动。

关系结果应区分：

- `UNRELATED`：检索到的候选项有充分证据表明它属于另一件事。
- `NO_MATCH`：检索没有找到可靠候选项。
- `INSUFFICIENT_EVIDENCE`：存在候选项，但证据过弱或相互冲突。

## 7. V5 AI：有边界的 Agent loop

### 目标

允许模型决定是执行搜索、读取偏好、提出问题、提出行动建议，还是在无需行动的情况下结束。

### 进入门槛

在 Agent 成为默认路径之前：

- 保存至少三个确实需要动态分支的任务。
- 将固定工作流作为 baseline 进行衡量。
- 比较完成情况、安全性、步骤数、延迟和成本。
- 记录 go/no-go 决策，说明由 Agent 决定工具选择是否带来了足够价值。

如果没有带来足够价值，则将 Agent 保留为实验路径，并继续使用固定工作流。

### 初始工具

| 工具                          | 类型           | 副作用                         |
| ----------------------------- | -------------- | ------------------------------ |
| `get_user_preferences`        | Read           | None                           |
| `get_current_item`            | Read           | None                           |
| `search_related_items`        | Read           | None                           |
| `retrieve_personal_documents` | Read           | None                           |
| `ask_clarification`           | Pause/proposal | 持久化一个问题，不执行外部写入 |
| `propose_new_action`          | Proposal       | 不写入权威产品状态             |
| `propose_action_update`       | Proposal       | 不写入权威产品状态             |
| `propose_action_cancellation` | Proposal       | 不写入权威产品状态             |
| `propose_calendar_export`     | Proposal       | 不执行导出                     |
| `finish_without_action`       | Terminal       | 无副作用                       |

确认行动、导出 `.ics`、发送通知或写入 EventKit 等权威命令，在第一个 Agent 版本中都不是
Agent 工具。

### 概念循环

```text
加载 run、checkpoint、产品版本和预算
-> 暴露本次 run 允许使用的工具
-> 模型选择一个后续动作
-> 后端校验工具、参数、用户范围和预算
-> 执行被允许的工具
-> 持久化 step 和 observation
-> 继续、暂停、结束，或在达到预算时停止
```

### 状态

```text
QUEUED
RUNNING
WAITING_FOR_USER
PROPOSAL_READY
COMPLETED
FAILED
CANCELLED
BUDGET_EXCEEDED
```

### 预算

第一个 Agent 具有以下限制：

- 最多五个步骤。
- 最大运行时间。
- 最大输入和输出 token 数量。
- 最大预估成本。
- 每个工具的调用次数限制。
- 重复调用相同工具的检测机制。

预算由后端强制执行。模型不能自行扩大预算。

### 暂停与恢复

当 Agent 提出问题时：

1. 持久化问题和 checkpoint。
2. 将 run 设置为 `WAITING_FOR_USER`。
3. 释放 worker。
4. 用户回答后，以幂等方式消费该回答。
5. 重新校验当前产品版本。
6. 从已保存状态恢复。

等待期间不要保持 HTTP 连接，也不要占用内存中的进程。

## 8. Agent 评测

### 轨迹用例

- 明确的预约：直接提出建议。
- 有歧义的预约：提出一个问题。
- 相关更新：执行搜索并提出更新建议。
- 取消通知：找到之前的事件并提出取消建议。
- 无需行动的通知：安全结束。
- 缺少检索证据：拒绝建立关联。
- Prompt injection：拒绝未授权行为。
- 工具循环：在预算内停止。
- 工具超时：产生可见的失败状态或重试决策。
- 服务重启后恢复。

### 指标

- 正确选择下一工具的比率。
- 任务完成或正确暂停的比率。
- 不必要的工具调用率。
- 平均步骤数、延迟、token 数量和成本。
- 正确停止率。
- 未授权工具调用尝试次数。
- 无效工具参数率。
- 用户接受建议的比率和编辑率。
- 恢复成功率。

“未授权行动成功执行”等安全指标必须为零，不能被隐藏在平均质量分数中。

## 9. Prompt injection 与工具安全

### 信任边界

- System/developer instructions 定义行为。
- 工具元数据定义被允许的能力。
- 用户回答提供数据和意图。
- 通知、上传文件和检索到的 chunks 都是不可信内容。

### 强制措施

- 每个 run 都使用工具 allowlist。
- 参数使用严格的后端 schema。
- 资源标识符在已认证用户的范围内解析。
- 后端重新计算授权结果，不信任模型提供的用户 ID。
- 建议的 hash/version 将用户批准绑定到准确值。
- 在产品具备明确的批准与幂等设计之前，不向 Agent 暴露外部副作用。

## 10. 模型与 prompt 生命周期

从第一次模型调用开始，记录：

- 提供商和模型标识符。
- Prompt 版本。
- 结构化输出 schema 版本。
- 输入和输出 token 数量。
- 延迟和预估成本。
- 停止或错误原因。
- 提取 run 或 Agent run 标识符。

发布模型或 prompt 变更之前：

1. 运行已保存的评测集。
2. 比较质量、拒绝行为、延迟和成本。
3. 检查回归，而不只是总体指标的提升。
4. 记录发布决策。

## 11. 框架引入规则

V1-V4 不需要 LangGraph。

单次调用、固定工作流、queue 和检索使用普通应用程序代码实现。只有当 V5 证明动态工具选择、
checkpoint、暂停/恢复和轨迹检查存在真实需求时，才考虑 LangGraph 或同类有状态 Agent 框架。

如果引入框架：

- 领域状态仍保存在 PostgreSQL 中。
- 框架 checkpoint 不替代权威产品状态。
- 工具授权仍由应用程序代码负责。
- 模型和提供商访问封装在项目边界之后。
- 应当能够替换框架，而不需要重写核心产品模块。

## 12. AI 掌握标准

只有当开发者能够做到以下几点时，才算真正掌握一个 AI 或 Agent 概念：

- 解释产品为什么需要它。
- 展示缺少它时系统如何失败。
- 区分模型、检索、工作流和基础设施失败。
- 实现有边界的能力。
- 使用正常、边界和对抗性用例进行评测。
- 观察其成本和延迟。
- 解释其权限边界和失败边界。
