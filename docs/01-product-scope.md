# LifeInbox 产品范围与原则

[English](01-product-scope.en.md)

## 1. 产品概述

LifeInbox 是一个个人生活通知收件箱。

用户可以粘贴日常通知，例如住房检查、大学截止日期、医疗预约、包裹取件、退货截止日期或订阅续费。LifeInbox 会保留原始来源，提出结构化的行动事项，在信息缺失时请求澄清，并帮助用户把已确认的计划导出到 Apple Calendar。

它的核心承诺是：

> 在三十秒内理解并安排一条重要的生活通知，同时不暗自编造日期，也不在未经确认的情况下采取行动。

## 2. 主要用户与初始场景

第一位用户就是产品开发者本人。

初始场景是一位居住在瑞典、会收到英语、瑞典语或中文通知的个人用户。默认时区为 `Europe/Stockholm`。

V1 采用 local-first，并且只面向单个用户。只有在 V2 实现身份认证和仅限所有者的授权后，它才会成为可通过多台设备远程使用的产品。

## 3. 问题陈述

日常通知经常把背景信息、日期、要求和无关文本混在一起。用户必须手动回答：

- 这是否需要采取行动？
- 它是预约、截止日期，还是时间灵活的提醒？
- 哪个日期是真正的事件日期，而不是消息发送日期？
- 下一步应该做什么？
- 这件事是否应该占用日历时间？
- 原始通知中的哪一部分支持提取结果？

将这些信息复制到日历中虽然只是小事，却会反复发生。遗漏一个日期可能带来实际损失。

## 4. 核心旅程

```text
粘贴通知
-> 保留原始文本
-> 提取零个或多个行动草稿
-> 展示证据和缺失字段
-> 用户编辑并确认
-> 提议 Apple Calendar 日历事件
-> 用户明确导出 .ics
-> 用户将事项标记为已计划、已完成或已忽略
```

后续版本会扩展这条旅程，而不是替换它：

```text
收到新的相关通知
-> 找到现有事项
-> 识别这是更新、取消还是新增要求
-> 展示旧值和提议的新值
-> 用户确认变更
```

## 5. 行动类型

### Appointment

占用一段日历时间的有明确时间范围的事件。

示例：

- 10:00 到 12:00 的公寓检查。
- 14:30 的牙医预约。
- 09:00 到 10:00 的面试。

必需信息：

- 日期。
- 开始时间。
- 结束时间，或者由用户明确批准的默认时长。
- 时区。

### Deadline

必须在某个日期前完成的事项。它不一定占用某个具体小时。

示例：

- 在 7 月 30 日前提交注册。
- 在 8 月 5 日前退回商品。

V1 将只有日期的截止事项表示为全天日历事件。系统不得编造午夜 UTC，好像来源中包含了准确时间。

### Reminder

由用户自行选择安排时间的灵活行动。

示例：

- 下周联系房东。
- 在续费前检查订阅。

如果来源表达模糊，系统会请求用户提供日期，而不是自行猜测。

### No action

有些消息只包含信息，不需要采取行动。`NO_ACTION` 是一种有效结果。模型不能强迫每个输入都变成日历事件。

## 6. V1 产品界面

### Inbox

- 粘贴一条通知。
- 查看最近的通知和行动事项。
- 按 `Needs review`、`Planned`、`Done` 和 `Ignored` 筛选。
- 当相同来源文本似乎被重复提交时发出警告。

### Review

- 展示不可变的原始文本。
- 展示一个或多个由 AI 提议的行动草稿。
- 展示重要字段的来源证据。
- 展示缺失或互相冲突的字段。
- 允许用户编辑每一个提议值。
- 确认、忽略或请求重试。
- 预览并导出 Apple Calendar `.ics`。

### Settings

- 默认时区。
- 默认预约时长。
- 默认提醒提前量。
- 摘要和问题的首选语言。
- 添加账户后提供数据删除控制。

## 7. 产品原则与不变量

### 先保留来源，再进行解释

原始通知会被保留。AI 输出绝不能替代原始通知。

### 先作为草稿，再成为事实

AI 输出始终是草稿。只有经过用户确认，才会产生具有权威性的行动数据。

### 不确定性必须保持可见

未知日期、互相矛盾的日期、缺失时间和模型失败都必须以可见状态呈现。它们不能被转换成看似确定的值。

### 重要字段必须有证据

日期、时间、地点、截止日期和必需行动应指向来源文本或用户提供的澄清。

### 外部副作用由人控制

没有用户的明确操作，系统不能导出或写入日历事件。

### 如实表示外部状态

Web 应用可以知道自己已经生成了一个 `.ics` 文件，但不能知道用户是否已经在 Apple Calendar 中完成导入。产品状态必须体现这种区别。

### 先保证可靠性，再提高自主性

可靠的存储、审核、测试和故障恢复，要先于自由运行的 Agent loop。

### 默认保护隐私

通知可能包含私人信息。默认情况下，日志不应包含完整通知文本、access token、signed URL 或文档内容。

## 8. 初始成功指标

只有在积累一小批真实数据后，才应该校准具体数值目标。

需要跟踪：

- 通过 schema 验证的模型输出比例。
- 明确日期和时间的提取准确率。
- 对模糊时间正确拒绝猜测的比例。
- 具有有效来源证据的重要字段比例。
- 用户在确认前编辑字段的比例。
- 从粘贴通知到确认行动所需的时间。
- 手动测试中的 `.ics` 生成和 Apple Calendar 导入成功情况。
- LLM 延迟、错误率、token 用量和预估成本。

## 9. 五分钟产品演示

1. 粘贴一条瑞典语或英语的住房检查通知。
2. 展示已保留的原始文本。
3. 展示提取出的日期、时间、地点、下一步行动和证据。
4. 修正一个特意设置为含糊的字段。
5. 确认该行动。
6. 导出 `.ics` 文件。
7. 在 Apple Calendar 中打开它。
8. 返回 LifeInbox，并将行动标记为已计划。
9. 展示提取元数据和审计/历史视图。

## 10. 非目标

V1 不包含：

- 自动访问 Apple Mail 或用户的整个收件箱。
- 直接登录 iCloud 或存储 Apple 凭据。
- 原生 iOS 或 macOS 应用。
- PDF、截图、OCR 或 `.eml` 解析。
- 团队协作、家庭共享或 RBAC。
- Redis、队列、worker 或向量检索。
- 通用聊天界面。
- Multi-Agent 编排。
- GraphRAG、fine-tuning 或自行托管推理。
- 自动作出医疗、法律、移民或财务决定。

进阶版本仍然聚焦生活通知，不会把 LifeInbox 变成没有边界的个人助理。
